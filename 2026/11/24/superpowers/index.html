Superpowers 使用手册：给 Coding Agent 的强制开发工作流

摘要

  • 本文写 obra/superpowers：它如何用一组可组合的 skill 约束 Agent 先想清楚再写代码，以及安装、升级、日常触发方式和完整 skill 列表。
  • 操作环境按 macOS，插件按 Superpowers 7.0.2。四端分别举例（命令行侧）：Claude Code、OpenCode V2（≥ 2.0.4）、Codex CLI、Cursor。换一台 Agent 就要各装一份；不含 Codex App。
  • 仓库与说明：obra/superpowers，OpenCode 专页，原始介绍。同系列见 Codegraph 使用手册：给 AI Agent 的本地代码知识图谱、记录 Claude Code、OpenCode、Codex-Cli 的 请求/响应 数据。

它解决什么问题

Coding Agent 默认倾向「听完需求立刻改文件」。需求还没对齐、边界没确认、测试基线没摸过时，这样写出来的东西很难一次可用，也难复盘。

Superpowers 把一套软件开发方法论做成 skill 库 + 启动时注入的引导。Agent 在会话一开始就会被要求：相关 skill 先读再动手。常见效果是——要做新功能时先走 brainstorming，设计通过后再 writing-plans，实现时套 test-driven-development，收尾走 finishing-a-development-branch。这些流程是强制的。

两块零件：

  • Skills：每个目录一份 SKILL.md，YAML frontmatter 写明何时必须启用、正文写清步骤与红线。

  • Bootstrap：多数宿主在会话开始（以及压缩上下文之后）注入 using-superpowers，逼模型先查 skill 再回应。

你通常不用手动点「启用 Superpowers」；装好插件、开新会话，说一句「做一个 React todo」这类需求，正常安装应先触发 brainstorming，随后才进入写文件。

基本工作流

一条完整功能大致按这个顺序串起来（中间会按场景跳过或并行）：

  1. brainstorming — 建设前先把意图、约束、取舍问清楚；小改动在对话里对齐，大项目落到可执行的设计文档。

  2. using-git-worktrees — 设计通过后，在隔离分支 / worktree 里开工，并确认测试基线干净。

  3. writing-plans — 把设计拆成 2–5 分钟粒度的任务，每步写清路径、改法和验证命令。

  4. subagent-driven-development 或 executing-plans — 按任务派生子 Agent 并逐步评审，或在当前会话内联实现、最后统一评审。

  5. test-driven-development — 实现阶段红灯 → 绿灯 → 重构；先写过实现再补测试的代码会被要求删掉重来。

  6. requesting-code-review — 任务之间对照计划做评审，严重问题挡住继续往下。

  7. finishing-a-development-branch — 测通后给出合并 / PR / 保留 / 丢弃等选项，并清理 worktree。

调试、并行子任务、收评审意见、声称「做完了」之前的核验，分别由后面的 skill 表覆盖。会话行为离谱时，用 diagnosing-superpowers 对着 transcript 查证据。

Skill 一览

本文按 7.0.2 仓库里的 skills/。名称就是 Agent 侧加载时用的 id（部分宿主会加 superpowers: 前缀）。

协作与交付

Skill 何时用
brainstorming 任何创造性工作开工前：新功能、改行为、规划
writing-plans 已有规格 / 设计，动手改代码之前
executing-plans 在本会话内联执行计划，或没有可用的子 Agent 工具
subagent-driven-development 计划可拆成独立任务，用子 Agent 逐项做并两阶段评审
dispatching-parallel-agents 两个以上互不依赖的任务可并行
using-git-worktrees 需要隔离工作区，或执行计划前要干净分支
finishing-a-development-branch 实现完成、测试通过，决定如何合回主线
requesting-code-review 大功能做完、合并前，或对照计划验收
receiving-code-review 收到评审意见后，落地前先核对其技术正确性

测试与调试

Skill 何时用
test-driven-development 写功能或修 bug 的实现代码之前
systematic-debugging 遇到 bug、测试失败或异常行为，提出修复之前
verification-before-completion 声称已修好 / 已通过 / 可合并之前，必须有命令级证据

元能力

Skill 何时用
using-superpowers 每次会话开始：如何发现与调用 skill
writing-skills 编写或修改 skill，并在部署前验证
diagnosing-superpowers 本会话（或指定历史会话）里 skill 没触发、乱触发、重复劳动、烧 token 等

技能优先级大致是：流程类 skill（brainstorming、systematic-debugging 等）先定做法，领域 skill 再落地。用户写在 CLAUDE.md / AGENTS.md 等里的项目说明优先于 skill。

安装总原则

  • 按宿主各装一份。 在 Claude Code 装过，不等于 Cursor / Codex / OpenCode 里也有。

  • 装完开新会话。 Bootstrap 与 skill 列表多半在会话启动时注入；旧会话里看不到是正常现象。

  • 验证「能列出 / 会自动触发」两件事。 插件出现在已安装列表，和「一说做功能就先 brainstorming」不是同一层。

装完后怎么用（跨宿主）

不必背命令。日常只需用自然语言描述目标；Agent 应按 description 自动选用 skill。已经确定要走某条流程时，可直接点名：

  • Claude Code / Cursor：输入 / + skill 名，例如 /brainstorming。

  • OpenCode：输入 @ + skill 名，例如 @brainstorming。

  • Codex CLI：输入 $ + skill 名，例如 $brainstorming（不要用 /）。

你真正要配合的是：

  • 回答澄清问题，并明确说「设计可以，按这个做」——brainstorming / writing-plans 在未批准前不应大面积改业务代码。

  • 需要跳过流程时说清楚，例如「跳过 brainstorming，直接改这三行」；用户指令优先于 skill。

  • 声称完成前看证据：verification-before-completion 要求先跑验证命令再下结论。
