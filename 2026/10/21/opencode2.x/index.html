摘要

  • OpenCode 官网，OpenCode 2.x 文档，OpenCode 下载页

  • 从 V1 迁移的官方说明

  • 1.x 的安装和基本用法见 opencode的安装和使用。

  • 把已经接好的模型暴露成本地 OpenAI 兼容接口，见 用 opencode-llm-proxy 把模型接到本地 OpenAI 接口。

  • 本文写 OpenCode 2.x 的安装、从 1.x 升级，以及升级后配置和日常命令的写法。2.x 文档以英文为准。

OpenCode 1 和 OpenCode 2 都提供 opencode 这条命令，默认不能并排安装。用包管理器装的 1.x，先卸掉再装 2.x。用安装脚本装的 1.x，改用下面的 2.x 脚本，它会替换旧二进制。

brew upgrade anomalyco/tap/opencode 和 1.x 里的普通更新都停留在 1.x。换到 2.x 是一次单独操作。

2.x 相对 1.x 改了什么

2.x 把原来挤在一个终端进程里的事情拆开了。会话、配置、登录、权限和工具执行放在当前用户的一个后台服务里；终端、桌面和网页都是连到这个服务上的客户端。1.x 的 opencode.json、agent、command、skill 和 .opencode/ 继续能读，2.x 在内存里归一化，不改写文件。后面几节里的 permissions、providers、mcp.servers 这些 2.x 字段，是把 1.x 里挤在同一个对象中的配置拆开。文件可以先保持 1.x 的写法，不必在升级前改完。

会打断现有用法的三处，以及配置不改也会变的行为，见下一节。

安装包和更新通道分开

1.x 的 npm 包是 opencode-ai，2.x 是 @opencode/cli。两条命令都叫 opencode，所以默认不能并排安装。1.19.2 起，1.x 的普通更新只看 opencode-ai 的 1.x 版本。升到 2.x 要显式执行 opencode upgrade --major、TUI 里的 /update，或按安装方式换包。

这样设计是为了让大版本停留在用户自己确认的那一次。Homebrew Core 的 opencode formula 跟踪 2.x；1.x 那篇用的 anomalyco/tap/opencode 继续提供 1.x。

一个用户一个后台服务

2.x 默认为本机用户启动一个共享后台服务。终端全屏界面、opencode mini、opencode run、桌面版，以及 opencode pair 打开的网页，连的是同一份会话和凭证。

服务集中保管状态之后，界面可以换，工作区不用各存一份。脚本和 CI 用 --standalone 起一个私有服务，避免把密钥写进共享服务。opencode service set disabled true 让本机命令默认都走私有服务；配对需要共享服务，关掉之后不可用。

界面配置从服务配置里拆出去

1.x 的主题、快捷键等可以写在多层 tui.json 里，包括项目目录。2.x 只保留一个全局文件 ~/.config/opencode/cli.json。后台服务不读它。首次启动、且这个文件还不存在时，会迁走全局 tui.json 里支持的项，并留下原文件。项目里的 tui.json 不迁，因为 2.x 的终端配置没有项目级。

服务配置回答「这个项目允许什么、用哪个模型」。客户端配置回答「这个终端怎么显示」。两份文件的优先级和生效范围因此不再缠在一起。

权限改成有序规则

1.x 的 permission 按工具分组，一组里面再写允许、询问或拒绝。例外规则和默认规则谁覆盖谁，要靠对象的合并顺序去猜。2.x 用一个有序的 permissions 数组，后匹配到的规则生效。宽规则写在前面，例外写在后面。

动作名也按实际做的事归类：bash 改为 shell，task 改为 subagent，write 和 patch 并入 edit。动作是字符串，插件可以再注册自己的动作。

policies 是另一层。权限规则可以允许，策略只能把结果收紧成拒绝，仓库里的配置放不开组织已经禁止的操作。受管配置和全局策略压过项目配置。

项目外路径单独用 external_directory 判断，默认允许。1.x 走出项目目录会先询问。2.x 把这件事从普通的读、写规则里拆出来，需要旧行为时自己加一条 ask。待办工具放到 experimental.todo，默认关闭，因为这组实验开关可能在后续版本里改掉。lsp 配置仍会被接受，2.x 不再启动语言服务器；原来靠它做的检查，改跑项目自己的 lint、类型检查或编译命令。

插件要有稳定 id

1.x 插件导出一个函数，返回工具和钩子。2.x 要求默认导出带 id，以及 effect 或 setup。id 用来区分插件存储和诊断信息。只把配置键从 plugin 改成 plugins，或把文件挪进 plugins/，旧函数仍然不会执行。

配置值也从「包名」或「[路径, 选项]」改成对象 { "package", "options" }。服务端插件和只在终端生效的插件分开：后者写在 cli.json，连到远程服务时仍然加载。2.1 再把各处的回放数据统一叫 native，自写插件和自写客户端要跟着改；终端日常使用不碰这组字段。

MCP 不再占满模型的工具列表

1.x 把每个 MCP 工具直接放进模型能看到的工具列表。服务器一多，上下文就被工具定义占掉。2.x 默认 codemode: true，这些工具归到对应服务器的命名空间里，由 execute 在 Code Mode 中调用。某个服务器必须走模型原生工具列表时，把它设为 "codemode": false。

配置形状也拆开了。服务器放在 mcp.servers 下，不再直接挂在 mcp 上。enabled 改成相反含义的 disabled。一个 timeout 拆成 startup、catalog 和 execution：列出工具通常只要几十秒，真正执行工具可以到数小时。远程服务器默认走 OAuth；只用 API Key 的服务要写 "oauth": false。OAuth 字段改为 client_id 这种蛇形命名，和配置文件里其余字段一致。

提供商、模型和 agent 按用途拆开

1.x 的自定义提供商把包名、接口地址和请求参数放在 npm、api、options 里。2.x 的 providers 把它们分成 package、settings、headers 和 body。AI SDK 的包加上 aisdk: 前缀，用来标明运行时。接口地址放进 settings.baseURL。

agent 的 prompt 改为 system，disable 改为 disabled，单独的 variant 接到模型名后面，写成 provider/model#variant。旧的 mode 映射变成 mode: primary 的 agent。命令里的 subtask 改为 subagent：交给子会话在后台跑，父会话保持原来的 agent 和模型。

压缩上下文的字段同样改了名字。preserve_recent_tokens 放进 compaction.keep.tokens，reserved 改为 buffer，表示留下来的上下文和预留空间。2.x 还可以按提供商选择本地摘要或提供商自己的压缩。

项目说明只发现 AGENTS.md

1.x 找不到 AGENTS.md 时会去读 CLAUDE.md。2.x 只自动发现 AGENTS.md，从 ~/.config/opencode/AGENTS.md 和当前目录向上直到项目根。目录里只有 CLAUDE.md 时，那些说明不会进入会话。.claude/skills 仍然会被发现，这和 CLAUDE.md 是两件事。要继续用原来的文件，把它写进 instructions，或把内容挪到 AGENTS.md。具体写法见「项目说明」。

终端之外的入口

1.x 的日常用法是在项目里执行 opencode，打开全屏终端。2.x 在这个服务之上加了几条入口：

入口 用来做什么
opencode 全屏终端，和 1.x 的主界面对应
opencode mini 轻量交互，适合不想占满屏幕的时候
opencode run 不打开界面，把回复打到标准输出，给脚本和 CI
opencode pair 生成一次性链接，用浏览器连到本机服务
桌面版 单独的安装包，和终端共用后台服务里的会话与凭证

免费模型和付费模型也分得更清楚。OpenCode Zen 上名字带 Free 的模型，以及 big-pickle，走 opencode/<模型 id>。自己在 providers 里配置的 key，例如 MiniMax 的按量接口，余额用完会返回 insufficient balance (1008)，换成 Zen 的免费模型 id 才不会打到那把 key。

升级时会碰到的变化

现有的 opencode.json、agent、command、skill 和 .opencode/ 可以继续用。2.x 在内存里识别 1.x 字段，不改写配置文件。日常终端用法可以先升级，再按需要改成 2.x 写法。

官方列出的三处不兼容：

项目 2.x 的要求
插件 按新的插件 API 重写。只改配置键或把文件挪进 plugins/，1.x 插件代码不会执行
服务端 API 和自写客户端 改用 @opencode/client 和 2.x 接口。2.1 又把回放数据字段统一成 native
终端界面配置 多层 tui.json 改为一个全局文件 ~/.config/opencode/cli.json，首次启动会迁移全局配置

就算配置一个字都不改，这几处行为也会变：

  • 项目外目录默认允许访问。1.x 会先询问。要恢复询问，加上 external_directory 的 ask 规则。

  • 待办工具默认关闭。需要时打开 experimental.todo。

  • lsp 配置仍会被接受，2.x 不启动语言服务器，也不提供 lsp 工具。原来靠 lsp 做的检查，改跑项目自己的 lint、类型检查或编译命令。

  • 远程 MCP 默认走 OAuth。只用 API Key 的服务要写 "oauth": false。

  • MCP 工具默认经 Code Mode 调用。要像 1.x 那样直接出现在工具列表里，给该服务器加 "codemode": false。

  • 会话分享在 1.19.1 已经停止，/share 和分享链接不再可用。

  • 项目说明只自动发现 AGENTS.md，不再把 CLAUDE.md 当作后备。详见「项目说明」。

macOS

在 2.x 内升级

Homebrew 安装的版本以 formula 为准，用 brew upgrade 保持和 formula 一致。升级前先退出正在运行的 opencode。

自动更新写在全局配置里，项目级配置里的同名字段不生效。默认是发现新版本后提示，不自动安装：

update 取值：notify（提示）、auto（自动安装）、disable（不检查）。自动安装不会重启已经在跑的后台服务，装完后执行 opencode service restart。

卸载会停掉后台服务，并删掉各版本共用的全局缓存。会话、配置和 state 会保留。包管理器安装会走对应的包管理器；安装脚本会打印删除二进制的命令。

从 1.x 升级到 2.x

升级前

退出所有 opencode 窗口，再备份配置。1.x 和 2.x 读写同一批配置路径，备份留到确认 2.x 可用之后再删。

项目里的 opencode.json、opencode.jsonc 和 .opencode/ 一并复制备份。先不要把配置改成只有 2.x 才认识的写法；回退到 1.x 时，1.x 读不了这种文件。

建议先把 1.x 升到 1.19 或更高，再做大版本切换。1.19.0 开始提供 opencode upgrade --major 和 TUI 里的 /update。1.19.2 起，普通更新只看 opencode-ai 的 1.x 版本，不会把 2.x 当成一次普通更新装上来。

Homebrew

1.x 那篇用的是 brew install anomalyco/tap/opencode。这个 formula 继续提供 1.x。

升级后遇到的问题

从 1.19 升到 2.x 后，打开 OpenCode 无法对话。用 /plugins 查看 superpowers 时会看到：

缓存里的 superpowers 仍是 v6.3.0 或更早。这些版本只导出 1.x 的插件函数，2.x 要求默认导出带 id 以及 effect 或 setup 的定义，所以加载失败。OpenCode 和 Bun 会把已经解析过的 Git 依赖留在 lockfile 和 ~/.cache/opencode 里。仓库里即使已经有 2.x 兼容代码，本地仍会继续加载旧包。配置键如果还是 1.x 的 plugin，也要改成 plugins。

项目配置和全局配置都要改。项目看 ./opencode.json、./opencode.jsonc 和 ./.opencode/opencode.json(c)。全局是 ~/.config/opencode/opencode.json，Windows 再检查 %APPDATA%\opencode\。升级后先写成带标签的地址，避免再次解析到旧 commit：

以前用 git clone 加软链装过 superpowers 时，把旧文件清掉，并删掉 opencode.json 里为它加的 skills.paths：

接着确认磁盘上的包是不是旧版，再清掉插件安装缓存。Windows 上对应目录在 %LOCALAPPDATA%\opencode\，删掉其中的 node_modules 和 package 相关文件。

重启会中断正在跑的会话。起来后 OpenCode 会按配置里的 Git 地址重新拉取。用下面几条确认服务端已经加载新插件。2.x 的插件在后台服务里加载，opencode run 要加 --standalone 才能在这次输出里看到加载日志。

在 OpenCode 里问一句 Tell me about your superpowers。能正常回答，说明插件已经加载。这时可以把配置末尾的 #v7.0.0 去掉，改回跟踪 main 的地址。去掉标签后如果仍是旧内容，按 Plugin 一节再执行一次 opencode service restart，必要时运行 opencode plugin update。

权限

规则是有序数组，后匹配到的生效。没有任何规则命中时才回退到询问。内置 agent 自己带一份基础策略，默认允许工具，读取 *.env 和 *.env.* 时询问，*.env.example 允许。用户配置接在基础策略后面。

1.x 那篇里的 bash / edit 例子，在 2.x 写成：

effect 为 allow（直接执行）、ask（询问）、deny（拒绝）。* 匹配任意长度，? 匹配一个字符。以 * 结尾的 shell 规则同时匹配不带参数的命令，所以上面的 git * 同时覆盖 git 和 git status。

搜索工具的动作是 grep，资源是正则本身。shell 里执行 grep 命令仍用 shell。这是两条规则。

要恢复 1.x「走出项目目录先询问」：

常用动作：read、edit（含 write 和 patch）、glob、grep、shell、subagent、skill、question、webfetch、websearch、external_directory。选择 Always 会把允许规则存进项目，且不能压过配置里的 deny。

组织级硬拒绝写在 policies 里。策略只能把结果收紧成拒绝，不能把拒绝改成允许。受管配置和全局策略压过项目配置。
