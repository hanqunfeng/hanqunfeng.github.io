npm简介

  • npm（Node Package Manager）是 Node.js 的包管理工具，也是 JavaScript 编程社区中最常用的管理和分享代码的工具。

  • 它允许开发者轻松地安装、共享、和管理在项目中使用的 JavaScript 包。

  • npm 分为两个主要部分：命令行工具（CLI）和 npm 注册表。

  • 命令行工具（CLI）：用于与注册表进行交互，安装和管理项目中的依赖。

  • npm 注册表：一个在线的数据库，存储了数百万个开源的 Node.js 包，开发者可以在自己的项目中使用这些包。

  • 从 Node.js 官网下载并安装 Node.js。

npx：临时执行包里的命令

npx 用来运行某个 npm 包提供的可执行文件（package.json 的 bin）。包已经在当前项目的依赖里时，直接跑本地的；本地没有时，临时下载到 npm 缓存目录，把该目录加入这次进程的 PATH 再执行。不会把这个包写进当前项目的 package.json，也不等于全局安装到 -g 目录。

从 npm 7 起，npx 与 npm exec（别名 npm x）是同一套能力；日常习惯写 npx，脚本里两者都可以。

找哪个可执行文件

未指定 --package 时，npx 把第一个位置参数当成包名（可带 @版本），再按下面规则选出要跑的命令：

  • 包的 bin 只有一个条目，或所有条目都指向同一命令：用那一个。

  • bin 有多个条目，且其中有一条与包名去掉 scope 后的名字相同：用那一条。

  • 仍无法唯一确定时退出并报错。这时要用 --package 明确指定包，再写出真正要跑的命令名。

包名不带版本说明符时，会优先匹配当前项目依赖里已安装的同名包。带了 @1.2.3 这类说明符时，只有本地依赖的名字和版本完全一致才算命中；否则会去拉远端。

npx 与 npm exec 的参数位置

npx 要求：所有属于 npx 自己的选项，必须写在位置参数（包名 / 命令）之前。包名后面的参数会原样传给被执行的命令。

拿不准某个包接受哪些参数时，查该包自己的文档；npx --help 只说明 npx / npm exec 本身。

临时包落在哪里

像 npx @deepseek-ai/dsh web 这类命令，不会把包装进项目的 node_modules，也不会装到 npm install -g 用的全局目录。本地项目依赖里没有该包时，它会下载到 npm 缓存目录下的 _npx 里，只给这次（以及之后复用缓存时的）执行用。

缓存根目录由配置项 cache 决定，可用 npm config get cache 查看。默认大致是：

系统 默认 cache _npx 下包的位置（示意）
macOS / Linux ~/.npm ~/.npm/_npx/<哈希>/node_modules/<包名>/
Windows %LocalAppData%\npm-cache %LocalAppData%\npm-cache\_npx\<哈希>\node_modules\<包名>\

<哈希> 由这次执行的包规格等算出，不同包、不同规格通常对应不同子目录。scoped 包路径里仍带 @scope，例如 @deepseek-ai/dsh 会落在 .../node_modules/@deepseek-ai/dsh/。

这和内容寻址的下载缓存 _cacache 不是同一层：npm cache clean --force 清的是包元数据/tarball 一类缓存；_npx 是 npm exec / npx 展开出的可执行环境。两者都可以占磁盘，清理方式也不同。

下次运行还要不要下载

缓存还在、且规格对得上时，一般不必重新下载，直接复用 _npx 里已有的目录，启动会快一些。

需要留意：

  • 没写版本号（例如只写 @deepseek-ai/dsh）时，npx 仍可能向 registry 查询是否有更新。已有新版本就会再下一份；没有更新则继续用缓存。

  • 写死了版本（例如 @deepseek-ai/dsh@1.2.3）时，同一规格更容易稳定命中已有缓存。

  • 删过 _npx、或整份 npm 缓存被清掉之后，下次必须重新联网下载。

想少触发“查最新版再决定是否下载”，在脚本和 CI 里给包钉版本。

注意点

  • 临时执行会跑 registry 上的代码。不熟悉的包名、未钉版本的 @latest，有供应链风险；生产脚本应钉版本，或改为项目依赖。

  • npx 成功只说明命令启动并退出码为 0；项目依赖是否按 lock 装好，仍要靠 npm ci / npm install 和后续测试确认。“缓存目录里能看到包”也不等于已经装进当前项目。

npm config timing

  • timing 是 npm 的一个 日志输出配置项，用于控制是否在命令执行时显示详细的时间信息，默认值为 false。

  • 当 timing 设为 true 时，npm 会在命令执行结束后 打印详细的时间统计信息，包括：

    • 每个子任务的执行时间（如解析 package.json、解析 node_modules、下载依赖等）
    • 网络请求的耗时
    • 依赖解析和安装的耗时
    • 整体执行的时间开销

  • 这对分析 npm 性能、优化依赖安装速度非常有用，特别是在大项目或 CI/CD 环境中。

    • 排查 npm 依赖解析、安装或下载过程的性能瓶颈

npm、pnpm、yarn 之间的联系和区别

  • 这三者都是 JavaScript 生态中的包管理工具，主要用于安装、管理和运行 Node.js 项目的依赖。它们的关系如下：

    • npm（Node Package Manager）是 Node.js 官方自带的包管理工具。
    • yarn（Yet Another Resource Negotiator）是 Facebook 开发的替代 npm 的工具，提供更快、更安全的依赖管理。
    • pnpm（Performant npm）是一个更高效的 npm 替代品，使用硬链接和去重机制来减少磁盘占用并加快安装速度。

  • npm、pnpm、yarn 的主要区别

特性 npm yarn pnpm

  • 什么时候使用 npm、yarn、pnpm？

    • ✅ 使用 pnpm（推荐）：
      1.你希望减少磁盘占用、加快安装速度
      2.你正在开发 monorepo（多包）项目
      3.你希望更高效地管理依赖

    • ✅ 使用 yarn：
      1.你希望更快的安装速度，但又不想改变 npm 传统结构
      2.你的团队习惯使用 yarn.lock 文件
      3.你在用 React Native（官方推荐 yarn）

    • ✅ 使用 npm（适合简单项目）：
      1.你希望使用 Node.js 官方的默认工具
      2.你不想安装额外的包管理工具
      3.你在开发小型项目，不需要 workspaces

npm 在 CI/CD 中的应用

流水线里依赖安装要可重复：同一提交每次装出的版本必须一致，package-lock.json 不能被安装过程改写。这一节写 CI 里常用的 npm 命令，以及它们和日常开发命令的分工。

npm ci：按 lock 文件干净安装

npm ci（别名 clean-install、ic、install-clean）专门给自动化环境和需要可重复构建的场景用。它只按 package-lock.json（或 npm-shrinkwrap.json）安装，不解析 package.json 里的版本范围去“找最新兼容版”。

对比项 npm ci npm install
依赖来源 只读 lock 文件 以 package.json 为准，必要时改写 lock
lock 与 package.json 不一致 直接报错退出 会更新 lock 去对齐
已有 node_modules 先整目录删除，再全新安装 增量安装，尽量复用已有模块
能否单独加包 不能，一次只装整个项目 可以 npm install <pkg>
是否写回 lock / package.json 从不写 可能写
典型场景 CI/CD、发布构建、要求依赖完全一致 本地开发、增删改依赖

具体行为：

  • 项目里必须有 package-lock.json 或 npm-shrinkwrap.json。没有 lock 时 npm ci 直接失败，不会退化成 npm install。

  • 会校验 package.json 与 lock 是否同步。lock 缺少声明的依赖，或版本对不上，立刻退出。

  • 执行前删除现有 node_modules，再按 lock 全量安装，结果干净、可重复。

  • 若当初生成 lock 时用过会影响依赖树形状的选项（例如 --legacy-peer-deps），npm ci 必须带同样选项，否则容易报错。可把该选项写进项目根目录的 .npmrc 并提交进仓库。

为什么 CI 优先用它：

  • 每次构建装到的版本与 lock 一致，减少“本地能过、流水线挂掉”。

  • 跳过版本范围解析，通常比 npm install 更快。

  • package.json 里的 ^ / ~ 不会在 CI 里悄悄拉到新版本。

  • lock 未提交或与 package.json 不同步时立刻失败，逼着把正确的 lock 提交上去。

使用前提：

  • 必须把 package-lock.json（或 npm-shrinkwrap.json）提交进版本库。两者同时存在时，npm-shrinkwrap.json 优先。

  • CI 可缓存 ~/.npm（对应配置项 cache），加速下载；缓存的是下载缓存，不是项目里的 node_modules。

  • 本地日常加包、升版本仍用 npm install / npm update；装完后把更新过的 lock 一并提交，再让 CI 跑 npm ci。

GitHub Actions 里常见写法（缓存 npm 下载目录）：

流水线里不要用 npm install 代替 npm ci 去做正式构建或发布前的安装。npm install 可能改写 lock，同一提交在不同时间装出的树可能不同。只有尚未提交 lock、或流水线本身就要改依赖版本时，才考虑在 CI 里用 npm install。

npm install-ci-test：干净安装后立刻测

npm install-ci-test（别名 npm cit、clean-install-test）等于先 npm ci，再立刻 npm test。既要严格按 lock 安装、又要跑测试时，一条命令即可。

package.json 里需要有可执行的 test 脚本，否则第二步会失败。

流水线里其他常用命令

这些命令并非只给 CI 设计，但在自动化里最常成套出现。

安全审计：npm audit

把当前依赖树提交给 registry，查已知漏洞。默认发现任意级别漏洞都以非 0 退出；CI 里常用 --audit-level 设定失败门槛，报告仍会列出更低级别的项，只是低于门槛时不让流水线失败。

跑项目脚本：npm run <script>

执行 package.json 的 scripts，例如 npm run build、npm run lint、npm test。pre* / post* 生命周期钩子在 CI 里同样会触发。

临时跑工具：npx

只需跑一次某 CLI、又不想写进依赖时用。完整说明见上文「npx：临时执行包里的命令」。

发布前预览打包：npm pack

确认即将打进 tarball 的文件列表，避免把本地配置或密钥带进去。以 --dry-run 的预览为准，对照 package.json 的 files 字段。

发布：npm publish

CI 自动发布的最后一步。长期 NPM_TOKEN 可以工作，但更推荐用 GitHub Actions 的 Trusted Publishing（OIDC），不必在仓库里存长期令牌。配置与工作流见 使用 GitHub Actions 和 OIDC 安全发布 npm 包；本地升版本、打标签、推送后交给 Actions 发布，可用 npm -- 用 npm-publish-oidc 发布包。

环境自检：npm doctor

在流水线或本机排查“npm 本身是否正常”时用：检查 Node/npm、registry 连通、权限、缓存等。能打印健康报告，不等于当前项目的 npm ci 或 npm test 已经成功。

一条最小 CI 顺序

安装失败时先看：项目根是否有已提交的 package-lock.json、npm ci 的报错是否在说 lock 与 package.json 不一致。审计失败先看 npm audit 的报告级别是否被 --audit-level 拦住。脚本失败先在同一环境手动跑对应的 npm run ...，确认是依赖问题还是测试本身失败。
